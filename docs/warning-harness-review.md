# 按人工审阅判定告警，而非追求清零

依据是用户提供的逐句批注 Word（79 条批注、37 处建议表述）、指标用途 Excel 和完整产物附件。示例金额不是核准事实，示例中的留空不是可以自动补造的数据。用户后续确认的指标定义及用途优先于旧定义；历史冻结来源不自动套用新定义。署名保持现状，章节数按内容需要决定。

## 本附件的告警裁定边界

当前质量检查输出 235 条 issue，不等于 235 个真实业务错误。原因可以在同一 issue 中重叠；图表的下游告警也依赖上游验证状态，不能相加当作独立错误数。

`scope_unknown` 既可能是旧事实没有登记信息，也可能是检查器尚不支持对应陈述。它不能通过默认“全院”消除。若事实中已有唯一、受信范围而检查器没有读取，才是可修复的误报。`statement_not_supported` 同样是当前证明不足，不直接等同于事实反证。

## Harness 应怎样判定正确

1. **给每个基准样本登记审阅编号和预期。** 不支持的断言、合法表述、待核实证据分别保存。R009/R070 区分预算时间属性；R014/R068 区分零与缺失；R030 区分开单和现金；R049 区分规模和风险；R052/R055 区分收入成本匹配；R058/R061 区分工作量和效率。指标选取另按 Excel 的 24 项、5 类用途以及 code/fieldRef 验证，不能凭同名选择。
2. **每个问题同时测正反例。** 如“执行率 80%，超预算”应报，“执行率 80%，低于预算”不应报；“月度事实＋月标签”应通过，“日度事实＋月标签”保持未知。还有凭证待核与已确认、完整总体与 Top-N 前缀、收入分析与预算分析的用途对照。缺证据的样本不能混入明确错误样本。
3. **做单因素变异。** 改金额、符号、单位、月份、科室、分母、事实指针或用途，检查相应诊断是否出现；恢复后重新验证。增加无关否定句、代码示例、重复标记等，验证不会误消警或误报。删除限定语后应重新暴露原先受限的经营断言。
4. **分层复跑。** 底层数值及身份；规划/用途/公式和期间；正文、图表、表格共同事实；实际编辑和 PDF/Word 产物。模型成稿另设留出样本，由业务审阅裁定，不由同一个模型自评后直接盖章。未运行、跳过、空样本及缺失评估必须明确记录。
5. **评价误报和漏报。** 报告 TP/FP/FN、precision、recall、已评估覆盖及 unknown 原因。不得把零输出当高准确率，也不能把未知项排除后声称整份报告通过。所有未知必须有原因及对应补证/实现动作。

业务信息不充分时，harness 最多可以判断“正确地保留了未知”，不能替代医院对预算版本、组织映射、收入归属、成本分摊和异常凭证的确认。79 条意见已映射不等于 79 条意见均已实现自动判定。

## 本轮已实现的基准与修复

运行：

```bash
MPLCONFIGDIR=/tmp/os-replay-mpl .venv/bin/python -m scripts.check_professional_review \
  --output /tmp/professional-review-harness.json
```

新增 27 个合成业务政策样本，对应 Word 中 11 个审阅编号，保存文档哈希、样本身份、预期诊断及结果；不是全部 79 条意见的自动验收，也不是业务盲评。输出逐样本 FP/FN、版本及样本哈希，非空唯一样本校验防止漏执行；预期会告警的样本在检查器完全静默时必须失败。

基准先复现 3 个漏报：一句中“预算版本无法确认”的无关限制抑制了后面开单收入推断现金、相关性推断效率、规模推断管理异常的诊断。现在仅检查对应推断及其直接支配的否定表达，额外回归“不能仅凭／无法通过／不应根据……”的合法限定。专业规则升为 professionalReview/2，进入既有质量身份，不改变发布下载策略。

27 个有限基准修复后 FP=0、FN=0，只说明此已知集合通过；真实附件本来没有命中这些有限专业模式，仍需针对当前 unknown 的结构化证据检查，不能拿这组成绩宣称业务验收完成。

验证：专业基准、原专业复核及表格/质量缓存回归 178 passed；工作流质量、纠错预算及全部 8 条发布/导出非阻断契约展开 110 passed。两个核心模块 mypy、三个 Python 文件 Ruff 和 diff 检查通过。附件质量回放仍为 197 个数值支持 unknown、16 对图表及依赖告警、5 个登记表告警和 1 个覆盖告警，未用关闭规则降低数量。

## 后续推进顺序

- 先把真实附件的 unknown 按“已确认误报、真实来源缺口、业务定义待确认、检查能力未覆盖”逐项建账；每条绑定定位、审阅编号、所需证据及责任环节。未核实前保留未裁定，不硬分成 bug 或业务错误。
- 从新计划入口完善已批准的用途、期间、范围、预算属性及可用公式。无授权不补全范围，不能用模板文字弥补事实缺项。
- 统一结构化表格和图表的来源投影，补注册而不造来源。先展示根因，再展开受影响的句子/表格/图表；汇总可以去重，原始诊断不可丢失。
- 根据 R003/R020/R057 的建议表述构造有同源事实的经营总览与结论矩阵，替代长章首句摘录；明确累计、同期、预算分母及缺项。避免为了核心结论页而重新引入未经证明的摘要。
- 持续加入业务人员裁定的留出样本。模型和规则修改都比较误报、漏报及证据覆盖，改善必须在同一冻结输入上可重现。

上述后续项是实施方向，本轮没有宣称全部完成。业务语义告警继续为软告警，可读且身份核验通过的 PDF/Word 继续交付，失败原因保留。

## 已推进：无损告警台账及编辑器语义摘要

对历史事实核对后，多个总量事实的 scope 确实为空；不能安全地默认成全院，也不能把组织层级空值改成已确认归属。因此本轮不通过填造范围来减少 unknown。

新增 `warning_ledger.py`：以现有质量结果和同报告、同修订的索引生成处理清单。原始 issue 每条恰好归属一个分组，可通过 issueIndices 回到完整诊断；同一冻结事实的多处引用形成一个处理分组，同一图表的数组与语义依赖合并展示。事实分组不表示这些句子具有同一个已确认根因，不同主体没有身份关联时不会合并。每组保存所有主体、事实 ID、原因、审阅编号、所需动作和建议处理阶段，不自动分派医院责任人。

判定状态始终是 `not_adjudicated`；范围未知仍为 unresolved，未执行证明单独标记 proof_not_evaluated，期间差异为 definition_review，绑定与规格缺口分别记录。新诊断或未识别原因保留为 unclassified，不静默删除或转为通过。所有建议来自人工审阅对应要求，不是对每个业务结论的最终裁定。

离线导出命令：

```bash
.venv/bin/python -m scripts.assess_report_warnings \
  --quality /path/to/quality-bundle-v1.json \
  --index /path/to/trace-index-v1.json \
  --output /tmp/warning-ledger.json
```

输入哈希用于记录所用文件身份，不替代调用方的来源授权及真实性校验；输出禁止覆盖输入。该导出是处理清单，不是新的报告验收器。

真实附件回放保留 235 条诊断，分成 55 组：33 个事实分组、16 个图表分组、5 个登记表分组及 1 个表格覆盖分组。真实编辑器 trace API 同样返回该台账，197 处绑定仍为 valid，403 个原文件哈希不变。235→55 只减少重复呈现，不表示剩余 55 个业务错误，更不表示通过了额外证明。

同时修复编辑器摘要漏显：来源可追溯但质量仍为 unknown 时，新增“语义待确认 N组”，保留来源状态，不把语义 unknown 改成引用失效或数值错误。已在来源复核中计数的同一主体、表格或图表不再重复计数；只使用输入身份相符的分组，旧服务端、分组缺失或过期时回退显示原诊断，不能因此漏显。可选台账生成失败时仍保留已完成质量检查和全部原始诊断。

验证：台账及质量/图表/表格集成回归 124 passed；原编辑器来源及全部 8 条发布/导出非阻断契约展开 212 passed；导出禁止覆盖输入及台账故障补验 5 passed（与前组重叠）。前端来源摘要、正文值和证据页 257 passed，摘要补验 29 passed（重叠）；TypeScript、生产构建及构建体积预算通过。两个新增模块 mypy、四个 Python 文件 Ruff 和 diff 检查通过。真实附件执行编辑器 trace 服务与台账导出，不代表已运行浏览器全流程或重新生成报告。

## 已推进：经营问题证据矩阵

依据 R003/R020/R057 的总览建议及 R002/R009/R033/R052/R061 的期间、预算和公式前提，新增 `management_overview.py`。这是经营总览的证据层，不是按章节摘句的摘要算法，也不自动授权自然语言条件与指标的映射。

- 保留所有冻结需求和分析完成条件；有需求但未登记完成条件时显式保留缺项，不能减少必答分母。历史无需求记录时 requiredQuestionCount 为 null，而不是 0 或“全部完成”。
- 仅在当前回答核验、问题身份、受信条件映射、所有必需正文主体、精确断言请求及来源身份均满足时列出服务端事实片段。每条保留断言、正文主体和来源哈希；片段带各自范围、期间和已支持运算，不能把不同窗口拼成统一经营结论。
- 未映射、来源失效、改金额、改范围、删除原句、引用选择器不符、重复断言或旧审核结果均不能携带已核验数值进入总览。条件未满足与未知分别保留，不把两者都称为财务错误。
- 不从展示名称推断预算/实际角色或跨用途选指标；沿用已批准的明确断言映射。用户 Excel 中同名不同用途的指标不会由这一层合并，也不会补造同比、预算分母、成本分摊或因果解释。
- 展示容量不足时整份矩阵标记不可用，完整问题及核验仍在原质量记录中；不截取部分满足项冒充完整总览。范围与金额缺失不补零，题目中的 Markdown 协议和 HTML 按文本展示。

矩阵接入真实质量记录和编辑器 trace 服务，随既有质量 sidecar 冻结；managementOverview/1 进入质量输入身份。生成异常记录为软告警，保留原有数值及回答审核结果；新增故障注入确认已生成且身份可读的 PDF/Word 仍签发下载链接。

可导出审核用 Markdown：

```bash
.venv/bin/python -m scripts.export_management_overview \
  --quality /path/to/quality-bundle-v1.json \
  --output /tmp/management-overview.md
```

导出针对指定、由调用方核验过的质量快照，重新构建矩阵而不照搬缓存矩阵；它不重新读取或授权底层数据，不替代对当前编辑内容的 trace 核验，且禁止覆盖输入。矩阵中的条件满足不等同于整份报告通过业务验收。

实际附件未登记需求审核映射，矩阵如实为 unavailable，不从历史正文猜出一个已核验总览；已有 235 条诊断、55 个处理分组及 197 个有效来源绑定继续保留。另用合成受信映射验证一项事实可展示、另一项缺口保留，以及编辑—撤下事实—恢复重新核验的完整闭环，合成示例不是用户报告财务数据。

本阶段没有替换 PDF/Word 核心结论页，也没有改变渲染投影或署名。下一阶段仍须把已批准的经营总览条件落实到新运行的明确指标/期间/范围映射，再将该证据层投影到正式总览；旧附件缺少的业务口径不自动猜测补齐。

总览复核同时发现并修复一个上游误判：断言编译器把空字符串、纯空格值及空范围键当成已知范围，可能发出受支持的断言。现在与 null 一样保留 scope_value_unknown，不默认全院，也不从已知院区推断未知科室；scopeValues/1 进入质量身份。总览再次检查范围、期间及单位，旧规则记录不自动升级为当前总览。

验证：断言、矩阵及质量集成 100 passed；矩阵边界扩展 24 passed（与前组重叠）；全部 8 条非阻断契约及 9 类质量故障注入 43 passed，增强索引保留故障断言另 1 passed（重叠）。4 个核心模块 mypy、8 个 Python 文件 Ruff 和 diff 检查通过。附件质量及真实编辑器服务已回放，保持原有诊断与绑定；已导出缺项说明及明确标记的合成示例，未重新生成正式 PDF/Word。
