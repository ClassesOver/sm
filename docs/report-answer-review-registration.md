# 正式报告的受信审核映射接入

经营问题总览只使用当前事实证明和明确的需求映射。映射接入现已贯通正式发布、原有 CAS 冻结、回答核验、质量 sidecar、编辑器重核及 PDF/Word。应用未配置映射提供方时保留原行为：缺项为 unknown，不从生成文本或展示名称推断批准关系。

## 服务端组装

`create_report_runtime(..., answer_review_plan_provider=provider)` 或 `ReportWorkflowRuntime(..., answer_review_plan_provider=provider)` 接收一个异步应用回调。类型见 `workflow.answer_registration.AnswerReviewPlanProvider`：

```python
async def provider(context: AnswerReviewRegistrationContext) -> AnswerReviewPlan | None:
    ...
```

回调应从业务已批准的明确规则或审核记录返回 `AnswerReviewPlan`；没有适用记录返回 None。不能调用模型后直接把生成的对应关系当作已批准映射，也不能从工作区、上传附件、会话状态或请求参数装载可执行回调。本入口不增加模型工具，不触发人工等待流程。

上下文由当前服务端质量计算构建，包含 report_id、revision、profile_hash、authorization_scope_hash、markdown_sha256、quality_input_sha256、冻结问题及当前登记的数值主体。每个候选保留 subject_id、fact_refs、number_reference、当前 assertion（可能为空）和 statement_verified；断言包含具体选择器、数值、单位、期间、范围及来源哈希。

业务集成必须按报告、授权范围、配置及问题身份选择批准记录；同名指标、同值、相似句子或分析项分配均不授权映射。应保留每个条件的全部必需主体，不能仅选择当前无告警的句子。未能编译的登记主体也保留在上下文中，不隐藏缺证据项。输入传给回调的是独立副本，回调不能通过修改候选内容改变服务端校验依据。

## 正式执行顺序

1. 首次装配追溯索引时，对当前冻结来源和正文执行独立质量核验；从权威状态读取冻结问题及既有审核计划。
2. 若已有冻结计划，重新验证问题身份并使用它，不调用提供方改写计划。既有计划损坏时仅拒用该计划，保留独立质量结果和原因。
3. 尚无计划且已配置提供方时调用回调。逐项核对冻结条件、主体身份及精确断言请求；不能用另一个金额相同的选择器代替。没有可核验请求的主体不能获得批准。提案无效时整份拒用，未截取成功子集冒充完整批准。
4. 通过原有 `freeze_answer_review_plan` CAS 命令冻结，核对返回的报告、问题和计划身份；冻结失败或回执不符时不得使用提案。成功后以冻结计划重新计算当前回答和经营总览，并随质量 sidecar 登记。
5. 恢复时复用不可改写的映射。编辑器读取冻结条件和计划，但重新核验当前正文及来源，不复用旧的 met 结果；导出只投影当前有支持的事实。

批准映射不等于证明事实。即使映射冻结成功，范围缺失、来源失效、期间无效或正文变化，仍可能得到 unknown/not_met。PDF/Word 的结构或投影身份通过也不等于整份报告业务验收通过。

## 失败、容量与交付

回调上限 10 秒；候选内容预算 2 MiB，计划预算 256 KiB，均完整或拒用，不静默截断必答条件。提供方异常、超时、提案非法、冻结失败和回执异常记录 `answer_review_registration_unavailable`，并保留具体失败阶段。独立断言、原始诊断及追溯索引继续登记；已生成且身份可读的 PDF/Word 仍签发下载链接。质量策略为 off 时不调用提供方。

HTTP 故障注入覆盖提供方、冻结、回执及既有计划损坏；集成回归使用真实索引构建、实际 Runtime、真实 reducer/CAS、编辑器服务、WeasyPrint、pandoc 和双格式验收。数据库用内存仓储替身，不调用真实模型；领域批准映射是明确标记的合成测试输入。

## 仍需业务接入

应用与 CLI 默认不注入提供方。本次完成的是可执行服务端入口及闭环验证，尚未替医院建立真实批准规则/审核记录，也没有从历史报告猜出映射。历史附件仍缺少登记需求及业务证据；新医院实例需由受信应用组装注入实际提供方。真实模型从头成稿、业务盲评、成本/灰度及生产部署仍未完成。署名及按内容分章的策略不变。
